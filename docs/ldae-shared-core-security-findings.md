# LDAE shared-core security hardening: Increment 2

This increment is limited to the shared core. It does not implement or claim a Linux collector, Windows collector, or Shadow Proxy. The implementation and tests are on `feature/ldae-shared-core`; platform-specific behavior still needs verification on Windows.

## Permanent development rules

These rules apply to every future CloudSentry change, not only this increment:

1. **Independent verification:** Every security claim needs a test.
2. **Fail visibly:** Missing telemetry must never look like a clean system.
3. **Least privilege:** Components get only the access they need.
4. **Evidence integrity:** Preserve original observations separately from conclusions.
5. **Continuous adversarial review:** Every new feature gets a failure-mode review before integration.

## Verification performed

- Focused `tests/test_core_engine.py`: **45 tests passed**.
- Full Python suite: **438 tests passed** (`PYTHONPATH=src python3 -m unittest discover -s tests`).
- Full suite output includes expected CLI error/permission-denied messages exercised by negative tests; test process exited successfully.
- Windows lock behavior, cross-platform filesystem semantics, real loaded-image hash provenance, and external custody/rotation of checkpoint keys remain unverified.

## Scope guard

No `main` changes, deployment configuration, collectors, active probing, or Shadow Proxy implementation are included in this increment. Do not describe the hash-chain journal as tamper-proof or path equality as verified binary identity.

## Recovery and recurrence: future acceptance criteria, not delivered

The user requested that recovery detect a listener reappearing, correlate its process with the original, preserve recurrence as a separate event, avoid killing a replacement without reauthorization, and record the full payload plus action/result/evidence. This increment does **not** implement a persistent listener watcher or process termination. The next continuity increment must treat these as acceptance criteria: retain the original observation and complete available raw payload (or bounded external evidence artifact with digest and visible truncation/completeness state), emit a linked recurrence event, use explicit assurance rather than PID-only matching, record action/result/evidence/authorization, and never auto-terminate a replacement without fresh authorization. The implementation plan records adversarial regression cases for each. Full payload means the full payload available to the collector, not data the collector cannot observe; sensitive-data access and retention still need least-privilege policy.

## Future Shadow Proxy session-control-plane direction, not delivered

The session-control mechanism controls only CloudSentry-owned proxy sessions and local resource allocation, never the connecting machine. Unknown identity is not maliciousness; IP identity/reputation cannot establish trust or justify blocking a shared VPN/cloud address. Future design should begin unknown sessions with bounded, restricted capabilities, progressively constrain only on observable behavior and policy, and separate policy violation from confirmed abuse. Local `INSPECT`, `SLEEP`, `RESUME`, `TERMINATE`, `BLOCK`, and `RELEASE` operations must be authenticated and audited with actor, target, policy revision, action/result, and evidence references. `SLEEP` affects only synthetic responses and resources on CloudSentry; `RESUME` remains policy-bound; temporary blocks are scoped and reversible. `ALLOW` cannot mean arbitrary forwarding: the original Shadow Proxy non-relaying rule remains in force, and only explicitly configured local/synthetic service capabilities can be allowed. This is an unimplemented design direction, not part of Increment 2.
